Nothing downstream (present pacing, vsync, any perf measurement of the present path) is meaningful until this is fixed. The fix already exists uncommitted in the working tree and only needs committing. Two -Wunused-variable/-Wmissing-prototypes diagnostics on the non-Apple legs ride along because they are in the same ui/ area, are one-line each, and would become hard failures the moment anyone adds --werror to the Windows legs.

### 2. Display/PVIDEO path correctness (nested finish abort, frozen overlay, stale composite)  (needs savestate: False)

Fixing it requires touching the same function that carries the PVIDEO upload cache and the pvideo image recreate bug, so the whole display.c cluster lands together. Second on the list because a crash/black-overlay on any FMV is a worse user outcome than the subtler draw-state bugs, and because it is self-contained in one file.

### 3. draw.c pipeline / dynamic-state / query-capacity correctness  (needs savestate: True)
Three high-severity fork-introduced state-tracking bugs that MoltenVK tolerates and native drivers do not: a clear pipeline can stay bound for a following real draw (the fork replaced upstream's accidental attribute-memcmp guard with a dirty flag); the dynamic-state skip caches are not invalidated when a pipeline specifies that state statically (blend constants after any full clear, line width, depth bias); and the REPORTS_FULL capacity guard finishes AFTER begin_pre_draw has already built the framebuffer and descriptor sets, producing framebuffers[-1] (a VkSemaphore handle handed to vkCmdBeginRenderPass) and descriptor_sets[base-1]. All three live in one file and share a validation-layer run, so they land together. The primitiveRestart revert rides along because it is a one-line revert to upstream in the same pipeline-creation function.

- files: hw/xbox/nv2a/pgraph/vk/draw.c, hw/xbox/nv2a/pgraph/vk/renderer.h, .claude/skills/xemu-architecture-contract/SKILL.md, docs/windows-gating-audit.md

Do not introduce a separate clear_pipeline_binding field. (2) begin_draw(), immediately after vkCmdBindPipeline and before the line-width compare: poison every cache whose state the newly bound pipeline specifies statically - cached_line_width when !has_dynamic_line_width, cached_depth_bias_* when !has_dynamic_depth_bias, and cached_blend_constants[0..3] when !has_dynamic_blend_constants (new PipelineBinding field: true in create_pipeline, partial_color_clear in create_clear_pipeline, false in pipeline_cache_entry_init). ### 19. perf: persistent decode thread pool for the OpenGL texture path  (needs savestate: True)
The GL renderer creates and frees a GThreadPool per upload - six times for a mipmapped cubemap - and for the very common levels == 1 case that is a full producer/consumer round trip with zero parallelism, plus real CreateThread cost on Win32 with its 8 MiB default stack reserve. The fork's own Vulkan renderer already does this correctly with a pool created once at init. Ranked low on the Windows list because Vulkan is the default renderer here, so this path is only hit as the documented triage workaround and as the init_renderer fallback - but it is exactly the path a Windows triager will be told to use.
